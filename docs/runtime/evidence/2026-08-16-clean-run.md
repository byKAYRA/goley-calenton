# Goley debugger-confound clean-run evidence

## Status and supersession

The original 30-second observation in this file is retained below as a
**provisional, insufficient control**. Its former conclusion that debugger
attachment caused `BinaryTr.bin+0x4ba17d` is retracted. A later clean control,
tagged `20260816-012720-clean75`, observed the same `ExitProcess` call site
with no debugger attached and with the target's debug-state predicates
measured directly.

Final decision: **x32dbg attachment is not required for the
`BinaryTr.bin+0x4ba17d` termination path.** This excludes debugger attachment
as the cause of that call. It does not prove an entirely instrumentation-free
environment: the required clean-room shim was injected, and the raw trace also
shows `windhawk.dll` activity.

`ExitProcess` followed shim readiness by exactly **795.886 ms**. Application
Error record `3788` names PID `0x1dc0` (`7616`), exception code
`0x80000003`, and fault offset `0x004ba17d` in `BinaryTr.bin`. The raw
`ExitProcess` record predates any debugger operation and is bracketed by
direct no-debugger samples. The Application Error's breakpoint exception is
not evidence of an installed breakpoint: exitguard returned from a call that
normally does not return, after which the client faulted at the recorded site.

The named-object sequence before termination was the same core sequence:
`NL59NPGL`, `Global\MtxNPGL`, its 9500-ms wait returning
`WAIT_OBJECT_0`, then `Global\MtxNPGM`. The wait report contains three
termination call sites. The raw trace also records `windhawk.dll` mutex
activity; that is reported as an uncontrolled hook/instrumentation confound,
not silently treated as a clean OS baseline.

### Final confound decision

The evidence excludes these hypotheses:

1. x32dbg GUI-process presence alone causes the call: its GUI remained open
   while MCP state was `stopped`.
2. x32dbg attachment is necessary: no attachment existed, the target's debug
   port/object/flags were clean, and `ExitProcess` still came from
   `BinaryTr.bin+0x4ba17d`.
3. An installed debugger breakpoint is necessary: none was installed, and the
   launcher/shim readiness path did not use one.

The narrower supported statement is therefore: **`+0x4ba17d` is a real
client termination path that reproduces without debugger attachment.** Its
upstream predicate remains unknown. The required shim and observed Windhawk
module mean this run does not exclude anti-hook or other instrumentation
sensitivity.
